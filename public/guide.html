The SecretDrop guide

A short-lived message, with control over how it is shared.

SecretDrop lets you encrypt a text message in your browser and share a link that needs a password to open. You do not need to create an account. The sender chooses an expiry time, and can keep a separate private link for manual deletion.

Share the right link

  1. Write your message and choose a unique password. The five-bar meter gives a rough strength estimate; it is not a guarantee that a password cannot be guessed.
  2. Choose 10 minutes, 1 hour, 1 day or 7 days. Pick the shortest time that gives your recipient a reasonable chance to read the message.
  3. Enable Burn After Read if the message should be removed after the first successful unlock in the app. Leave it off if the recipient needs to return before expiry.
  4. Press Encrypt & Generate Code. Copy the recipient link from the success screen and send it to the intended person.
  5. Send the password through a separate channel. For example, send the link in email and communicate the password in a call. This reduces the risk of a single forwarded conversation containing both.

Keep the private delete link to yourself. It is a separate sender credential. Anyone who has it can delete your message. Save it before creating another secret; SecretDrop has no account-based recovery for lost sender links.

What Burn After Read actually does

The recipient enters the password, and their browser attempts to decrypt the message. An incorrect password does not burn it. After successful decryption, the app sends a read confirmation and waits for the server to delete the record before displaying the message. The Self-destructed badge means that deletion was confirmed.

Deletion does not erase screenshots, copied text or data a recipient has already saved. A modified client could also keep the encrypted data or withhold read confirmation. Treat the recipient as someone you trust, rather than treating deletion as control over their device.

Expiry and deletion are different

Expiry starts when the server creates the message, not when someone first opens the link. Once that time is reached, the API refuses further unlocks. Expired database records are not automatically physically purged on a schedule. Sender deletion and confirmed burn remove the message from the live database table.

If a link has stopped working, it may have expired, been deleted by the sender, or already been burned. Ask the sender for a new message if you still need it. There is no password reset or message recovery feature.

Reading the view counter

The number shown after unlocking counts unlock requests, including incorrect-password attempts and repeated requests from the same person. It is not a count of unique people and cannot prove that someone else read the text. For example, two password mistakes followed by a successful unlock will produce three attempts.

What encryption covers

The browser uses the password to encrypt text before sending it to the API. The normal sharing flow does not send the plaintext or password to the server. The service still handles encrypted content and metadata such as message codes, timestamps and attempt counts. Read the privacy overview for the storage details and limitations.
